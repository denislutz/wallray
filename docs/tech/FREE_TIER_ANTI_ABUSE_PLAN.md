# WallRay — Free Tier Anti-Abuse Implementation Plan

Layered defense for the free tier (2 requests per verified email, AI-only, no expert; €9.99 per
additional analysis beyond that — payment enforcement for the overage is not built yet, see Phase 0
item 1 below). Goal: make the realistic abuse case cost more than it's worth, and cap worst-case
spend even if every layer above it fails. Partially implemented — the rest is the plan to execute
later.

Context: `be/app/api/routes/auth.py` already does email-OTP verification (no password signup) —
this is a stronger starting point than plain email-in-a-form, but it does **not** by itself stop
disposable-inbox farming or Gmail alias tricks. Each layer below closes one gap the OTP flow
leaves open.

---

## Current state (what already exists)

| Mechanism | Where | Covers |
|---|---|---|
| Email OTP required before any account/session exists | `be/app/api/routes/auth.py` (`/auth/otp/send`, `/auth/otp/verify`) | Blocks non-interactive form-spam (no real inbox = no code) |
| Per-user report cap | `be/app/core/config.py` — `free_tier_limit` (default `2`, `FREE_TIER_LIMIT` env var) / `free_tier_limit_expert` (default `50`, `FREE_TIER_LIMIT_EXPERT` env var), checked against `user.report_count` in `upload_job.py`'s `execute()` | Right number now, and configurable per environment without a code change — but still a hard block, no paid-overage path yet (that's the rest of Phase 0 item 1) |
| Resend free-tier send cap | 100 emails/day (noted in `AUTH_PLAN.md`) | Accidental soft ceiling on total signups/day until Resend is upgraded |
| `slowapi` rate limiting | Noted as TODO in `AUTH_PLAN.md:250`, not yet added | Nothing enforces per-IP limits today |

Bypass vectors still open: Gmail dot/plus aliasing (one real inbox → unlimited "unique" emails),
disposable-mail domains (unlimited real-but-throwaway inboxes, scriptable), no per-IP throttle on
`/auth/otp/send`, no CAPTCHA, no global daily ceiling independent of per-user tracking, and the
free-tier's AI cost sits on the same Anthropic API key/budget as paid traffic.

## Phase 0 — Quick wins (code only, no new infra, do first)

   - `be/alembic/versions/` — new autogenerated migration for the column (see `CLAUDE.md` schema-change workflow)

   - `be/tests/test_upload.py:17,143` — already imports `_FREE_TIER_LIMIT` and seeds `report_count=_FREE_TIER_LIMIT`; add a paid-user case that isn't blocked at the same count

   `select(UserRow).where(UserRow.email == ...)` lookups in `send_otp` (line 63) and `verify_otp`

   - `be/app/adapters/persistence/pg_user_repo.py` — `get_or_create_by_email` (line 65) and `get_by_emails` (line 76) also key off raw email; normalize on the way in
   - `be/tests/test_auth.py` — add cases asserting `a.b+x@gmail.com` and `ab@gmail.com` resolve to the same user

   - `be/pyproject.toml` — add the blocklist package (or vendor the list — see next line) under `dependencies` (~line 8-40)

   - `be/tests/test_auth.py` — add a rejection case for a known disposable domain (e.g. `mailinator.com`)

## Phase 1 — Rate limiting + CAPTCHA (code + one new dependency) — ✅ DONE (2026-07-11)

1. **Per-IP rate limit on `/auth/otp/send`.** Wire up `slowapi` (flagged as a TODO at
   `docs/tech/AUTH_PLAN.md:250`, not yet a dependency anywhere in `be/pyproject.toml`) — e.g. 3 OTP
   requests per IP per hour, 10/day. This is the fix for the other half of the OTP gap: nothing today
   stops a script from hammering `/auth/otp/send` itself (which is also a mail-bombing vector against
   Resend's sending reputation, independent of the free-tier cost question).
   - `be/pyproject.toml` — add `slowapi` under `dependencies` (~line 8-40)
   - `be/app/main.py` — instantiate `Limiter`, register the rate-limit exception handler, add `SlowAPIMiddleware` alongside the existing `CORSMiddleware` block (lines 51-59)
   - `be/app/api/routes/auth.py` — add the `@limiter.limit(...)` decorator to `send_otp` (line 51); needs a `Request` param added to the handler signature
   - `be/tests/test_auth.py` — add a test asserting the Nth request from one client IP within the window gets 429
2. **CAPTCHA on the sign-in form.** Cloudflare Turnstile (free, privacy-friendlier than reCAPTCHA)

   path entirely.
   - `fe/ui/business/SignInPage.tsx` — render the Turnstile widget in the `step === "email"` branch (lines 71-108), capture its token, pass it into `handleSendCode`/`sendCode.mutate()`
   - `fe/services/tech/AuthS.ts` — `sendOtp` (line 85) needs a `turnstileToken` param added to its body payload
   - `be/app/api/routes/auth.py` — `_SendRequest` (line 35) gains a `turnstile_token: str` field; `send_otp` (line 51) verifies it server-side against Cloudflare's siteverify endpoint before line 59's OTP generation
   - `be/app/core/config.py` — new `turnstile_secret_key` setting (alongside `resend_api_key` at line 50)
   - `docs/tech/DEVOPS.md` — add `TURNSTILE_SECRET_KEY` (BE) and `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (FE) to the env var tables (lines 180-198, 198-206)
   - `.env.local.example` / `be/.env.prod` / `be/.env.test` / `fe/.env.prod` / `fe/.env.test` — add the new keys (gitignored, real values pasted by hand per `DEVOPS.md:177-178`)

**Implementation notes (deviations from the plan above, discovered while building it):**

- Rate limiting is gated by `enabled=not settings.debug` on the `Limiter` itself
  (`be/app/core/rate_limit.py`), not a header — CI/e2e hit `/auth/otp/send` multiple times per run
  against the shared test deploy (global-setup.ts × 2 + auth.spec.ts + the CI warmup curl), which
  would trip "3/hour" within a single run under a real per-IP limit. Since `DEBUG=true` on test and
  `false` on prod (see `DEVOPS.md`), this reuses the same debug-gated pattern as the E2E fake-AI
  header instead of inventing a parallel mechanism, and sidesteps the self-throttling problem
  entirely rather than working around it.
- Turnstile verification uses a separate debug-gated bypass, `X-E2E-Skip-Turnstile: 1`
  (`be/app/api/routes/auth.py`), honored only when `settings.debug` is true. This one *is* header-based
  because it has to be — `global-setup.ts`'s `loginViaOtp` mints session cookies via a raw Node
  `fetch()` with no browser, so it can never produce a real widget token. `auth.spec.ts` (the one
  spec that drives the real sign-in UI) goes through the actual widget + a real Cloudflare
  siteverify call instead of this header.
- Cloudflare's public "always passes" dummy test keys (`1x00000000000000000000AA` site /
  `1x0000000000000000000000000000000AA` secret) are wired as the default in
  `fe/services/tech/EnvS.ts::turnstileSiteKey()` and in every local/test env file — safe to commit
  since they're published testing credentials, not secrets. **Prod still needs a real site+secret
  pair from the Cloudflare dashboard**, set via `TURNSTILE_SECRET_KEY` (BE) and
  `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (FE) — until that's done, `turnstile_secret_key` stays empty in
  prod and verification silently no-ops (same default-off convention as `resend_api_key`).
- `be/Dockerfile`'s uvicorn command gained `--proxy-headers --forwarded-allow-ips='*'` — without it,
  `get_remote_address` (the rate limiter's key function) would see Traefik's container IP for every
  request behind Coolify's reverse proxy, making the "per-IP" limit a single shared global bucket.
  Not in the original file list; found while implementing.
- Fixed two adjacent, pre-existing bugs discovered while touching this code: the CI e2e warmup curl
  (`.github/workflows/ci.yml`) posted to `/auth/otp/send` without `terms_accepted`, which 422'd ever
  since the terms-checkbox requirement shipped — added the missing field. `AuthS.sendOtp` (FE) never
  checked `res.ok`, so a rejected request (400/429/anything) was silently treated as success by the
  sign-in form — fixed so `sendCode`'s `onError` toast actually fires, which is otherwise the whole
  point of this phase being visible to a blocked user.

## Phase 2 — Global ceiling, independent of per-user/per-email tracking

1. **Daily global cap on free-tier submissions.** A single counter, `date`-keyed in Postgres — confirmed
   today there is no Redis/cache adapter anywhere in `be/app/core/` (only `config.py`, `container.py`,
   `db.py`), so a new ORM row is the path of least resistance rather than adding a new infra dependency.
   Incremented in `upload_job.py` alongside the per-user check. If the platform-wide free-tier count for
   the day exceeds a fixed number (start conservative — e.g. 50/day, tune once real signup volume is
   known), free-tier submissions are rejected (paid submissions unaffected — this cap only applies to
   the free path, using the paid flag added in Phase 0) until the counter resets at midnight.
   This is the layer that guarantees a hard ceiling on daily spend *regardless* of how well an
   attacker evades Phases 0–1 (e.g. distributed across many IPs/residential proxies).
   - `be/app/adapters/persistence/orm_models.py` — new `DailyFreeTierCounterRow` (`date` PK, `count` int), next to `UserRow`/`OtpTokenRow` (lines 12-36)
   - `be/alembic/versions/` — new migration for the table
   - `be/app/domain/ports/user_repo.py` (or a new small port, e.g. `be/app/domain/ports/free_tier_counter.py`) — add the read/increment contract
   - `be/app/adapters/persistence/pg_user_repo.py` (or a new `pg_free_tier_counter_repo.py` beside it) — implement the counter read/increment
   - `be/app/application/upload_job.py:130-141` — check the global counter alongside the existing `user.report_count >= _FREE_TIER_LIMIT` check in `execute()`, increment on success
   - `be/app/core/container.py` / `be/app/api/deps.py` — wire the new repo/port into `UploadJob`'s constructor injection (mirrors how `job_repo`/`user_repo` are already provided)
   - `be/tests/test_upload.py` — add a test that trips the global cap independent of any single user's `report_count`

Effort: ~half a day — one counter table/key, one check, one reset job (or just `date`-keyed rows).

## Phase 3 — Blast-radius containment (infra/account + a small amount of routing code)

1. **Separate Anthropic API key + budget for free-tier traffic.** In the Anthropic console, create
   a second API key (or workspace) used only by the free-tier code path, distinct from
   `ANTHROPIC_API_KEY` (`be/app/core/config.py:26`) used by the paid Assess/Verify pipeline. Add
   `ANTHROPIC_API_KEY_FREE_TIER` to the BE env vars and route the free-tier model call through it.
   The account-console step is pure config, but picking which key a given job uses is code — traced
   today via `container.py` → `AnthropicAdapter(api_key=settings.anthropic_api_key, ...)` (line 31-36)
   → `deps.py::get_vision_llm` (line 42-48, currently only branches on the E2E fake-AI header) →
   consumed in `be/app/api/routes/jobs.py:69` and the pipeline nodes under `be/app/application/pipeline/nodes/`
   (`ai_assessment.py`, `intake_gate.py`) via `be/app/application/run_assessment.py`.
   **Why this matters:** without this, a runaway free-tier abuse that trips a shared spend cap
   takes paying customers' report generation down with it — an accidental self-inflicted outage on
   top of the abuse itself.
   - `be/app/core/config.py:26` — add `anthropic_api_key_free_tier: str = ""`
   - `be/app/core/container.py:12-43` — build a second `AnthropicAdapter` (or `fake_vision_llm`-style second field on `Container`) using the free-tier key
   - `be/app/api/deps.py:42-48` (`get_vision_llm`) — branch on the requesting user's paid flag (added in Phase 0) to return the free-tier vs. paid adapter, same pattern as the existing `x-e2e-fake-ai` branch
   - `docs/tech/DEVOPS.md:180-198` — add `ANTHROPIC_API_KEY_FREE_TIER` to the backend env var table
   - `be/.env.prod` / `be/.env.test` / `.env.local.example` — add the new key (gitignored, real values pasted by hand)
2. **Hard spend limit on the free-tier key**, set in the Anthropic console, with alerts at
   ~50%/80% of the limit. This is the last-resort circuit breaker — tuned low enough that a worst-case
   bypass of every layer above still can't produce a surprise bill, but high enough it doesn't trip
   on legitimate week-one traffic. Revisit the number after Phase 0's real "Quick Check" launch
   gives actual signup/day data. No files — console-only.

Effort: ~half a day (routing code) + ~1 hour console-only for the spend limit.

---

## Suggested execution order

Phases 0 → 1 → 2 → 3, in that order — each phase closes a cheaper/more common attack path than the
next, and Phase 3 is pure safety net that should exist regardless but matters least if 0–2 are done
well. Phase 0 alone (30 min of code) eliminates the majority of realistic abuse at zero infra cost;
treat 1–3 as hardening once the free tier is actually live and getting real traffic.
