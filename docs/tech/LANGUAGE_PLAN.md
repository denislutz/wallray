# Language Handling — Implementation Plan

Extends Phase 2. Parent plan: `docs/BE_PHASE2_PLAN.md`.

---

## Problem Summary

Three actors speak different languages:

| Actor | Language | When |
|---|---|---|
| Customer | EN / DE / RU (any supported) | Writes a short description at upload; receives the final PDF |
| AI | English (best output quality) | All intermediate internal state |
| Expert | DE or RU (set once on their account) | Reads AI classification; writes review notes |

The report must be delivered in **two languages** whenever expert language ≠ customer language:

- `report.pdf` — customer's language
- `report_expert.pdf` — expert's language

When languages match, only one PDF is generated.

---

## Language Transition Map

```
Customer (short description + photos)
    ↓  no translation — minimal text, LLM reads anything natively

[classify] → English internal state (always)
    defect_type:  "crack"              ← controlled vocab, EN
    severity:     "high"               ← controlled vocab, EN
    notes:        "Hairline crack..."  ← prose, EN, internal only

[expert_notifier]
    → look up expert.preferred_language from User row
    → translate notes → expert's language (one short LLM call)
    → write expert_language to state
    → send deep-link email (classification shown in expert's language)

[Expert reads in DE/RU, writes review notes in DE/RU]

[synthesize]
    inputs:  EN notes + DE/RU expert_notes
    outputs (one call, two targets):
        summary              → customer_language
        summary_expert       → expert_language   (null if same as customer)
        expert_note_localized → customer_language (expert notes translated for customer)

[GenerateReport]
    render report.pdf        → summary in customer_language
    render report_expert.pdf → summary_expert (only if not null)
    email customer: report.pdf
    email expert:   report_expert.pdf (or report.pdf when same language)
```

---

## Cross-Session Rules

- `classify()` output is **always English** — no language param, ever
- `notes` on `DefectClassification` is the English AI output — internal, never shown to customer directly
- `summary` is always in customer_language — generated by `synthesize()`
- `summary_expert` is in expert_language — generated in the same `synthesize()` call, null when languages match
- Expert's preferred language comes from `User.preferred_language` — never hardcoded, never derived from job
- `expert_language` is written to `AssessmentState` by `expert_notifier` after looking up the expert User row
- `GenerateReport` reads `job.expert_language` (stored on Job after notifier runs) — no second User lookup
- The expert-facing translation of `notes` (for the review email + page) is done in `expert_notifier` via a short LLM translate call
- All other translation is handled by `synthesize()` — no separate translate node, no translation service
- DB reset required after Session 1 (new columns on `users` and `jobs`)
- RU is a first-class UI language — `ru.ts` must stay in sync with `en.ts` key-for-key; `de.ts` is the reference for how DE was done

```python
async def translate(self, text: str, target_language: str) -> str:
    """Translates short text to target_language (ISO 639-1 code)."""
    response = await self._client.messages.create(
        model=self._model,
        max_tokens=512,
        system="You are a translator. Return only the translated text, nothing else.",
        messages=[{
            "role": "user",
            "content": f"Translate to {target_language}:\n\n{text}"
        }],
    )
    return response.content[0].text.strip()  # type: ignore[union-attr]
```

### `be/app/application/pipeline/nodes/expert_notifier.py`

Changes:

1. Look up `expert.preferred_language` from the User row (already fetching the expert).
2. Write `expert_language` to state.
3. Translate `state["classification_notes"]` to `expert_language` via `vision_llm.translate()`.
4. Pass the translated notes into the email (new `classification_notes` param on `send_expert_review_request`).

```python
def expert_notifier(job_repo, user_repo, email, vision_llm, app_url):
    async def _node(state):
        expert = await user_repo.get(state["assigned_expert_id"]) if state["assigned_expert_id"] else None
        expert_lang = expert.preferred_language if expert else "en"
        expert_email = expert.email if expert else ""

        notes_for_expert = state.get("classification_notes") or ""
        if notes_for_expert and expert_lang != "en":
            notes_for_expert = await vision_llm.translate(notes_for_expert, expert_lang)

        await job_repo.update_status(state["job_id"], JobStatus.expert_review,
                                     expert_language=expert_lang)
        review_url = f"{app_url}/expert/review/{state['job_id']}"
        classification = state["defect_classification"]
        await email.send_expert_review_request(
            to=expert_email,
            job_id=state["job_id"],
            review_url=review_url,
            defect_type=classification.defect_type if classification else "unknown",
            severity=classification.severity if classification else "unknown",
            classification_notes=notes_for_expert,
        )
        return {"expert_language": expert_lang}

    return _node
```

## What Is Deliberately Out of Scope

- **Non-expert path localisation**: the customer-language PDF on the non-expert path still renders English `notes` prose. A `localise_classification` step can be added later as a Phase 3 item.
- **Translation service**: all translation happens via the same Vision LLM (Anthropic). No separate translation API or library.
- **RTL languages** (Arabic, Hebrew): template not adapted for RTL rendering.
- **Language auto-detection**: customer picks their language explicitly on the upload form; no Accept-Language inference.

## Session 6 — Language Rules Under the Pipeline Redesign

**Context:** `defect_classifier`/`classify()` (cheap model, images, English-only) → `report_generator`/`GenerateReport` calling `synthesize()` (strong model, **text-only relay of the classifier's 1–2 sentence notes, no images**) is being replaced by a richer node shape: `intake_gate` (role/validity check) → `ai_assessment` (strong model, full images + context every call) → optional bounded `customer_after_questions` loop (reserved, starts at `0`) → optional `expert_synthesis`. Every rule below carries forward unchanged from Sessions 0–5 — this section only maps them onto the new node names and calls out what the redesign fixes or extends.

**Unchanged contract:**

- Internal state stays English-stable. `ai_assessment` replaces `classify()` as the producer of the stable internal representation — call this field `reasoning_en` (structured Befund/Ursache/Schweregrad/verification-items text), successor to today's `classification_notes`. Still never shown to the customer directly, still the only thing `translate()` is ever called on.
- Customer- and expert-facing prose is still **natively generated per language in the same model call**, never translated from an English draft. `ai_assessment` produces `summary` in `customer_language` directly, exactly as `synthesize()` does today — this is the behavior confirmed to matter (it's why the direct single-shot Fable-5 test outperformed the app: no relay step diluted it).
- `translate()` remains reserved for narrow, display-only uses (expert review email, admin GET localizing `reasoning_en`) — never for the primary customer/expert report body.

**What the redesign fixes:**

- Both surviving synthesis call sites — the no-expert path (was `report_generator` → `synthesize_report()`) and the post-expert path (was `GenerateReport.run()` → `synthesize_report()`) — currently call the strong model with **no images**, only the classifier's short text. `ai_assessment`/`expert_synthesis` must pass the actual photo bytes every time, matching what `classify()` already does today. This is the single biggest quality gap identified against the direct Fable-5 comparison, independent of language.
- Collapsing `classify()` + `synthesize()` into one `ai_assessment` call means the cheap-model, zero-domain-context English pass no longer exists as a separate step — `reasoning_en` and `summary` (customer_language) come out of the same rich call instead of a thin call followed by a polish call.

**Forward-looking — `customer_after_questions` loop (currently `0`, inert):**

- When active, `clarifying_questions`/`verification_items` of kind `customer_question` must be generated **natively in `customer_language`** by `ai_assessment` itself, not drafted in English and translated — same rule as `summary`, extended to cover Q&A prompts. No new translate call gets added for this loop; if it ever needs one, that's a rule change to flag here first.
- `qa_history` (customer's answers) feeds back into `context_signals` in whatever language the customer replied in — `ai_assessment` reads it natively on the next loop iteration, same as it reads the original photos/description natively today. No pre-translation to English before re-invoking the model.
